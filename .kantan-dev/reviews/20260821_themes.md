## Scope beyond the plan

All of it was a consequence of the plan rather than an addition to it, but it is
recorded here so it is visible:

1. **`Themes::Drops::PageDrop` + `page` assign.** The layout and the content
   template render separately, so a variable set in the content template is not
   visible to the layout. Without this the theme could not emit `<title>` or the
   og: tags the ERB views already produced — an SEO regression on an app whose
   whole point is a lossless WordPress migration.
2. **`Themes::Uninstaller`.** Implied by task 10's uninstall action; extracted as
   a service to keep the controller thin, per the repo's conventions.
3. **`KantanPress::Config.site_title` / `site_description`.** A theme layout
   needs the site name; hardcoding "Kantan Press" in a theme would be wrong.
4. **`KantanPress::PlainText` and a double-escaping fix.** See Fixed #4 below.
5. **Eager-loading `:author` and `:categories`** in the four public controllers.
6. **`config/initializers/rubyzip.rb`.** One line, load-bearing for the
   zip-bomb defence.

## Findings, all fixed during review

### Major

**1. `Themes::Renderer` cached parsed templates in a plain `Hash`.**
`app/services/themes/renderer.rb` — Puma serves requests on several threads, and
a `Hash` rehashing while another thread reads it is not safe. Now a
`Concurrent::Map`.

**2. `Themes::Registry.all` re-scanned the filesystem on every request.**
`app/services/themes/registry.rb` — it lists two directories and parses a
manifest per theme, and it is called once per page render *and* once per
theme-asset request. A single post view with a stylesheet, a script and four
font files meant six full rescans. Now cached in production, keyed on the mtime
of the two theme roots so an install or uninstall invalidates it; outside
production it still rescans every call, so editing a theme in place shows up on
reload. Covered by three new examples.

**3. `Themes::Installer` claimed a rollback it did not perform.**
`app/services/themes/installer.rb` — on overwrite it moved the existing theme
aside to `previous/`, with a comment saying this protected against a failed
rename. It did not: the `ensure` deleted the staging directory unconditionally
and nothing restored it, so a failure between the two moves left the site with
no theme. There is now a real `rescue` that puts the old theme back, a
`SystemCallError` rescue in `#call` that reports a full disk as an error rather
than a 500, and a spec that stubs the move to fail and asserts the old version
survives.

### Minor

**4. Excerpts were HTML-escaped twice — a pre-existing bug, now fixed.**
Visible on the running site as `All&#39;s well` in every excerpt. Two causes,
both in `PostsHelper#excerpt_plain_text`: Rails' `strip_tags` leaves entities
encoded, and the `truncate` *view helper* escapes its result and marks it
`html_safe`, so output escaped it again. Extracted to
`app/lib/kantan_press/plain_text.rb` (strip comments → strip tags → decode
entities → squish) and switched to `String#truncate`, which has no escaping
semantics. Fixes the ERB views as well as the theme.

**5. `Theme#bundle` re-resolved through the registry on every call.** Validations
and the settings merge each ask for it. Memoised per slug.

## Advisory — not fixed, deliberately

**A. The default theme's byline publishes the author's email local part.**
`User` has no display name, so `PostDrop#author_name` derives one from
`email_address` — `marvin.baltazar@gmail.com` renders as `marvin.baltazar`. This
is normal for a personal blog and matches the reference design, but it is new
public information the ERB views never showed, and it reveals the sign-in
identifier. Removing it is deleting one line from
`themes/independent/templates/post.liquid`; a proper fix is a display-name field
on `User`. Left as-is because it matches the reference the feature was specified
against — flagged for the owner to decide.

**B. Category, tag and month archives do not paginate.** Pre-existing; the
repo's own conventions call for it. Out of scope here, and unchanged by this
work.

**C. No theme partials.** `{% render %}` has no file system wired up, so the
summary markup is duplicated between `index.liquid` and `archive.liquid`. The
plan listed five templates and no partial support. Documented as a limit in
`docs/THEMES.md`.

**D. Settings types are `color`, `select` and `boolean` only.** As specified.
`text` and `number` would be a natural next step for third-party themes;
documented as a limit.

## Found after review, by the owner, and fixed

**6. The admin themes page never showed a screenshot (Major).**
`app/views/admin/themes/index.html.erb` built
`theme_asset_path(path: "screenshot.svg")`, but screenshots sit at the bundle
root and `Bundle#asset_path` only resolves inside `assets/`, so the card image
404'd for every theme. It went uncaught because the admin spec's fixture themes
shipped no screenshot at all. Fixed with a dedicated
`GET /themes/:slug/screenshot` route and action, keeping the root location that
`docs/THEMES.md` documents and that WordPress themes use. The regression spec
now asserts the URL the page builds actually serves.

**7. An uploaded theme could have scripted the site's origin (Major).**
Noticed while fixing 6. `Bundle::ASSET_EXTENSIONS` includes `.svg`, and an SVG
opened as a document executes its own `<script>` — so a theme zip containing one
was same-origin XSS against whoever followed the link. Every theme asset
response now carries `Content-Security-Policy: default-src 'none'; style-src
'unsafe-inline'; sandbox` and `X-Content-Type-Options: nosniff`. No effect on
SVGs in `<img>`, or on CSS/JS/font subresources.

**8. The theme's body copy and reading column were both too small (Major).**
Reported by the owner against a side-by-side with the reference. Two values were
read out of the reference CSS without their media-query context:

- `.entry-content { font-size: 1.063rem }` is the *small-screen* size. At
  `32.375em` (518px) the reference sets `font-size: inherit`, i.e. the 1.1875rem
  body size. The theme was serving 17px at every width instead of 19px.
- `#content-wrapper` is `max-width: 700px` at base but `max-width: 1080px` with
  40px padding at `62em` (992px) — a 1000px reading column on desktop, not 700px.

Both fixed, with the column now a `--measure` custom property that steps at
992px, and `.wrap`/`.cover-meta` switched to `content-box` so the padding sits
outside the measure as it does in the reference. Measured in a browser at
1920px: 1000px column, 19px copy. Two regression specs pin the values.

**9. A wrong `wp_attachment_id` could never be healed by re-importing (Major).**
Also from the owner's report — a post showed no featured image. Root cause was
in the importer, not the theme: `register_media` used
`item.wp_attachment_id ||= wp_attachment_id`, so a row that already carried the
wrong id kept it forever. In this database the spec fixture had been imported
into development at some point, giving `qwen3_web_search_result.png` the
fixture's id 901 — which really belongs to `rubocop_ale.png` — and the real
export could never correct it. Every post whose `_thumbnail_id` pointed at the
true id silently lost its featured image.

Now an explicit claim that releases the id from whichever row wrongly holds it,
so the export stays the source of truth and a re-run heals the database. Four
specs cover it. Re-running the existing export took the affected install from 90
to 91 featured images with no duplicates and no errors.

**10. A media row can claim "stored" while its object is gone (Minor, follow-on).**
The broken cover on `local-llm-tool-calls` was not the theme and not the
importer: the object was genuinely absent from the bucket, while the row said
`stored`. One root cause covers finding 9 and this one — the spec fixture was
imported into the development database on 2026-08-08 while
`KANTAN_STORAGE_BACKEND` was still `disk`. The row's `uploaded_at` matches, to
the second, the mtime of the only file that has ever been in `public/media/`.
That single import both wrote the image to disk instead of S3 and stamped the
fixture's attachment id onto it.

`retry_media` could never repair it, because the row was not `awaiting_fetch`.
Added `Wordpress::MediaVerifier` and `rake wordpress:verify_media[reset]`, which
heads every stored object and reports the drift — 6 specs. Against the real
bucket: 228 checked, all present after the restore.
