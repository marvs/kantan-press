## What was built

A theme engine for the public site, plus the theme that ships with the app.

- **Admin → Themes** lists installed themes, activates one, installs one from a
  `.zip`, uninstalls an uploaded one, and edits the settings a theme declares.
- Themes are written in **Liquid**, so an imported third-party theme cannot run
  Ruby, read the database, or reach the S3 credentials.
- **Independent**, the theme in the box, is a port of Raam Dev's Independent
  Publisher: a full-width cover image carrying the post title, which fades out
  as the page scrolls; PT Serif body, PT Sans everything else, self-hosted; no
  sidebar.

There is no React work in this feature. The repo's React dependency is only the
vendored Gutenberg bundle, and the editor is deliberately untouched.

## Architectural decisions

**The filesystem owns theme content; the database owns only the choice.**
A theme is a directory. Built-ins live in `themes/` in the repo; uploads are
unpacked into `storage/themes/`, which Kamal keeps on the `kantan_press_storage`
volume. The `themes` table holds `slug`, `active` and a `settings` JSON blob and
nothing else. One read path serves both kinds, uninstalling is `rm -rf` plus a
row delete, and a theme upgrade is replacing files.

**Liquid, not ERB.** ERB templates from a stranger are arbitrary Ruby. Liquid is
a sandbox: a template reaches only the drops it is handed. This is the single
decision the rest of the design follows from.

**Drops escape by default.** Liquid does not escape output, and Jekyll/Shopify
convention leaves `| escape` to the theme author. That is the wrong default
here — a theme that forgets it turns an imported WordPress title into stored
XSS. So text fields come back already escaped and raw HTML is reachable only
through a field named `*_html`. Comment bodies are the one field the public
wrote, so they are sanitized rather than escaped. **This is the rule most likely
to surprise someone who knows Liquid from elsewhere**; it is documented at the
top of `docs/THEMES.md`.

**The ERB views stayed, as a production fallback.** A theme error raises in
development and test, and in production is logged before rendering the app's own
ERB view. The whole feature is additive, and a broken theme cannot take the site
down.

**The app computes head metadata, not the theme.** `PageDrop` carries title,
description, canonical URL and og: image. The layout and the content template
render as two separate Liquid passes, so a variable set in one is not visible in
the other — but more importantly, a WordPress migration lives or dies on its
canonical URLs, and that should not depend on a theme author getting them right.

## Migration

`20260821120000_create_themes` — `slug` (unique index), `active` (boolean, not
null, default false), `settings` (json, not null, default `{}`). A **partial
unique index on `active WHERE active`** enforces one active theme in the
database, not just the model: two active rows would make the site's appearance
depend on row order.

## Security posture

The zip upload is the only place in the app where a browser upload causes files
to be written and read back as code-ish content, so it is treated as hostile:
an upload cap (10MB), an **uncompressed** cap (50MB — a zip bomb is small on
disk, so the compressed size proves nothing), an entry-count cap, an extension
allow-list, and refusal of any entry that is a symlink or would write outside
the theme directory. Nothing is written to `storage/themes` until the whole
archive passes and the extracted result validates as a theme; the last step is a
rename inside the same filesystem, with the previous version restored if it
fails.

`.liquid` and `.json` are deliberately **not** servable, so a theme cannot serve
its own source. Liquid resource limits cap render length and score per render,
with a fresh budget each time.

Every theme asset response carries `Content-Security-Policy: default-src 'none';
style-src 'unsafe-inline'; sandbox` and `X-Content-Type-Options: nosniff`. An
SVG opened as a document runs its own `<script>` on this origin, and themes are
untrusted, so an uploaded theme could otherwise script the admin's browser the
moment someone followed a link to it. The policy has no effect on SVGs loaded
through `<img>`, or on CSS, JS and fonts loaded as subresources.

## Type scale and measure — do not "tidy" these

They come from the reference and were both wrong on the first cut, because the
values were read without their media-query context:

| | small screens | wider |
|---|---|---|
| Body copy (`.entry-content`) | `1.063rem` | `inherit` (= `1.1875rem`) from 518px |
| Reading column (`--measure`) | 700px | 1000px from 992px |

`.wrap` and `.cover-meta` are `box-sizing: content-box`, so the horizontal
padding sits *outside* the measure — that is how the reference's
`#content-wrapper` works, and switching them to `border-box` would silently
narrow the column. Two specs in `spec/requests/independent_theme_spec.rb` pin
both values.

## Gotchas

- **`ThemeAssetsController` calls `skip_forgery_protection`.** Rails refuses to
  serve a JavaScript response to a non-XHR request — a guard against dynamic JS
  carrying user data being read cross-origin. A theme's `theme.js` is a static
  public file, so the guard does not apply; without this every theme script 422s
  *after* the file is sent, which is a confusing way to find out.
- **Rails' `truncate` view helper escapes its result and marks it `html_safe`.**
  Use `String#truncate` for anything that will be escaped again on output.
  `strip_tags` also leaves entities encoded. Both bugs were live before this
  feature and showed up as `All&#39;s well` in every excerpt.
- **An endless `def` with a trailing `if` applies the modifier to the
  definition**, not the body — `def next_page = n + 1 if n > 0` evaluates the
  condition at class-body time. Bit once in `PaginationDrop`.
- **A braceless string-keyed hash is parsed as keyword arguments** when the
  method has any keyword parameter. `theme.assign_settings({ "k" => "v" })`
  needs the braces.
- **Saving settings for the default theme creates an inactive row.** Nothing is
  marked active until someone presses Activate, so `Theme.selection` looks up a
  row matching the fallback bundle's slug — otherwise those settings would
  silently do nothing.
- **A theme's screenshot is not under `assets/`.** It sits at the bundle root
  (`themes/<slug>/screenshot.svg`), matching WordPress, so it has its own route
  and action — `Bundle#asset_path` only ever resolves inside `assets/`. Linking
  a screenshot through `theme_asset_path` 404s.
- **Registry caching is production-only.** Editing a theme in place in
  development shows up on the next request; in production the cache invalidates
  on the theme roots' mtime, which covers install and uninstall.
- The uncompressed-size cap reads the zip's own central directory, so
  `Zip.validate_entry_sizes` must stay true or a crafted archive could
  understate it.

## Follow-ups built in the same session

**Compact index cards.** The first cut rendered each index entry's featured
image at 100% of the column. These are screenshots, not photography — 2490x1434
and larger — so a ten-post index came to 8,170px, about one screen per post. The
reference avoids this by serving a cropped 700x430 thumbnail rather than the
original. Entries are now a card: a 200x125 `object-fit: cover` crop beside the
text, stacking on mobile. Same page: **2,431px**, and entry heights went from
765-953px and wildly variable to a uniform 154-180px. `align-items: flex-start`
matters — without it the thumbnail stretches to the row height and the declared
aspect ratio stops meaning anything.

**Admin -> Settings.** Site title, tagline and posts-per-page, in a
`site_settings` key/value table read through `KantanPress::Config#site_setting`,
which checks the database before ENV. Deliberately the reverse of `#setting`,
which ENV wins — see the note in `CLAUDE.md` about splitting configuration by
who owns it. `Admin::SettingsController::FIELDS` is the allow-list, so a
submitted `s3_secret_access_key` is dropped rather than stored. Values are
memoised on `Current` for the length of a request, so a change made by another
Puma worker is picked up on the next one.

**Empty terms are hidden from `site.categories` / `site.tags`.** The home page
nav was listing a category with nothing in it while hiding one with 35 posts —
`limit: 8` over an alphabetical list of *all* terms. Both drops now join to live
posts and carry a `live_posts_count` selected with the row, so `post_count` is
free rather than a query per term.

## Known limitations

- **No theme partials.** `{% render %}`/`{% include %}` have no `Liquid::FileSystem`
  wired up, so summary markup is duplicated between `index.liquid` and
  `archive.liquid`. Wiring one up scoped to the bundle's `templates/` is the
  natural next step.
- **Settings types are `color`, `select` and `boolean`.** `text` and `number`
  are a change to `Themes::Setting::TYPES` plus a branch in `_setting_field`.
- **No sidebar or widget areas.** Deferred in the idea.
- **The editor is not themed.** An explicit non-goal.
- **The byline publishes the author's email local part**, because `User` has no
  display name. See advisory A in the review.
- Category, tag and month archives still do not paginate (pre-existing).

## How to verify

```bash
bundle exec rspec        # 352 examples
bundle exec rubocop
bundle exec brakeman
bin/rails server
```

The theme specs worth reading first are
`spec/requests/independent_theme_spec.rb` (the real theme, real files) and
`spec/requests/themes_spec.rb` (the engine, including the production fallback).
`spec/support/theme_fixtures.rb` builds throwaway theme directories and zips;
point `Themes::Registry.builtin_root` / `uploaded_root` at a tmpdir with
`allow(...).to receive_messages(...)` and the whole engine is testable without
touching the repo's own themes.

In the browser: `/admin/themes` to install or switch, then any post. A post with
a featured image gets the cover treatment; one without falls back to a titled
header. Checked at 375px, 768px and 1280px.
